# Canvas Design Studio v1.1.0 — Agent Handoff

**Date:** 2026-05-16
**Version shipped:** 1.1.0 (npm: `canvas-design-mcp@1.1.0`)
**Audience:** Any agent or developer picking this up cold — Codex, Gemini, Claude, or human

This document explains what changed in v1.1.0, why the decisions were made, every question that came up during design and implementation, and what comes next.

---

## What v1.1.0 Is

v1.1.0 ships **SP13 — Worksheet Reader**. It solves one problem: the setup wizard asks for values professors have to look up (hex colors, Canvas URL, API token path). Without preparation, they stop mid-wizard to hunt for these. v1.1.0 lets professors fill out `setup-worksheet.md` at their own pace, then hand the completed file to the wizard which pre-fills every prompt automatically.

**It adds:**
- `get_setup_worksheet` tool — returns the blank template with AI-host instructions prepended
- `worksheetContent` parameter on `setup_institution` — pre-fills all wizard prompts from a completed worksheet
- `formatWorksheetSummary()` in wizard — shows pre-filled values before prompts; masks API token as `✓ (provided)`
- Worksheet tip in `get_started` no-config and partial-config states
- `docs/setup-worksheet.md` added to npm `files` array so it ships with the package
- Node.js installation instructions (Windows/macOS/Linux) added to `docs/installation.md`

**It does not change:**
- Any existing tool parameters or return shapes
- The wizard's interactive flow when called without `worksheetContent`
- `institution.json` schema
- Any tool other than `setup_institution`

## Design Questions and Decisions

These are the questions that were explicitly debated during design. Each records what was decided and why.

### Q1: What should trigger the worksheet flow?

**Options considered:**
- A. AI host reads the file from disk and passes it to the tool
- B. The MCP server reads the file itself from a known path
- C. Professor pastes the file contents directly into chat

**Decision: A — AI host reads the file and passes contents via `worksheetContent` parameter.**

Why: The MCP server is stateless and has no knowledge of where the professor's working directory is. Option B would require a path parameter and filesystem access that breaks the tool's security model. Option C is impractical for a multi-kilobyte file. Option A is consistent with how all other content flows through MCP tools in this codebase (`ingest_assignment_folder` follows the same pattern — the AI host reads the folder, assembles content, passes it in).

### Q2: What should the wizard UX feel like when a worksheet is provided?

**Options considered:**
- A. Silent pre-fill — just load the defaults, no indication to the professor
- B. Summary-then-confirm — display all pre-filled values before the first prompt, then let the professor confirm or override each

**Decision: B — summary-then-confirm.**

Why: Option A would confuse professors who don't remember what they wrote on the worksheet. They'd see their values pre-filled without understanding where they came from. The summary block makes the connection explicit and sets the expectation ("Press Enter to accept each value, or type to override") before any prompt appears. This is the UX that `git rebase -i` and similar "here's what I'm about to do" tools use.

### Q3: How much of the worksheet should be parsed?

**Options considered:**
- A. Core fields only (institution, colors, Canvas URL, API token)
- B. Everything including philosophy answers and Panopto credentials

**Decision: B — parse everything, make the template accessible.**

Why: The worksheet already has all the fields. Parsing a subset creates a two-tier experience where some prompts pre-fill and others don't, which is more confusing than a consistent "everything pre-fills" behavior. Philosophy answers are the most time-consuming section of the wizard — pre-filling them has the highest value per field.

### Q4: How should `get_setup_worksheet` be structured?

**Options considered:**
- A. `worksheetContent` parameter on `setup_institution` + `get_setup_worksheet` tool to fetch the template
- B. A standalone `setup_institution_from_worksheet` tool that takes a path
- C. `worksheetContent` parameter only, no fetch tool

**Decision: A — both the parameter and the fetch tool.**

Why: Option B adds a tool that's confusable with `setup_institution`. Option C leaves no way for an AI host to get the blank template without already having it — defeating the purpose. Option A cleanly separates "get the blank template" from "run the wizard with pre-filled values", and the `get_setup_worksheet` description includes the full AI-host workflow in plain language so the host knows exactly what to do.

## Implementation Decisions

These are the decisions made during implementation, including issues that came up during code review.

### `@inquirer/prompts` `password()` has no `default:` option

The `@inquirer/prompts` `password()` prompt does not support a `default:` parameter — unlike `input()`, there is no way to pre-populate a masked field. The workaround used for both the Canvas API token and the Panopto client secret:

1. If `defaults?.apiToken` is present, print a console message before the prompt: `✓ API token from worksheet — leave blank to use it, or type a new token to override.`
2. After the prompt: `const apiToken = apiTokenInput || defaults?.apiToken || ''`

The `||` operator is correct here because `password()` returns `''` when the user presses Enter without typing — falsy, so it falls through to the worksheet value.

Both fallback lines have a comment in the code: `// password() has no default: option — use worksheet value if user leaves blank`

### Philosophy answers: `''` not `undefined` for blank entries

The spec said blank philosophy answers should be stored as `undefined` (sparse array). The implementation stores `''` (empty string) instead. This is a conscious deviation:

- The wizard uses `defaults?.philosophyAnswers?.[i] ?? ''` as the default
- `undefined ?? ''` → `''` and `'' ?? ''` → `''` — both work correctly
- The actual behavior is identical either way

The important implication: do NOT use `!== undefined` as a guard when checking philosophy answers. Use truthiness (`if (answer)`) because blank worksheet answers are `''`, not `undefined`.

### `extractLabeledField` regex escaping

`extractLabeledField` in `src/utils/worksheet.ts` builds a regex from a caller-supplied `label` string. The two current callers pass `'Client ID'` and `'Client Secret'` (no metacharacters), but the function escapes the label before building the regex:

```typescript
const escaped = label.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
const regex = new RegExp(`${escaped}:\\s*(.+)`);
```

This was added during code review. The fix is a precaution for future callers — a label like `'App (v2)'` would break without it.

### `brandUrl` parsing: `Your answer:` not `Brand standards URL:`

The spec described `brandUrl` as a labeled field (`Brand standards URL: ___`) requiring `extractLabeledField`. The actual `docs/setup-worksheet.md` uses a `Your answer:` line like every other section. The implementation correctly uses `extractYourAnswer` — the spec was describing a format that doesn't exist in the real file.

If the worksheet format is ever changed: update `parseWorksheet` in `src/utils/worksheet.ts` and the corresponding test in `tests/worksheet.test.ts`.

### `panoptoClientId` visible in summary, `panoptoClientSecret` masked

`formatWorksheetSummary` shows `panoptoClientId` in plain text (it is a non-secret identifier analogous to a username) but intentionally omits `panoptoClientSecret`. There is a regression test in `tests/wizard.test.ts` asserting that the secret does not appear in the summary output.

### Summary display guard

```typescript
// Only show the summary if the worksheet provided at least one field
if (defaults && Object.values(defaults).some(v => v !== undefined)) {
```

`Object.values` on a `WizardDefaults` with all fields explicitly set to `undefined` returns an array of `undefined`, so `.some(v => v !== undefined)` returns `false` — the banner correctly does not appear. In practice, `parseWorksheet` only assigns fields it actually found, so the returned object only contains present values and the guard is always `true` when a meaningful worksheet is passed.

The `!== undefined` check (rather than truthiness) is intentional — it handles `0` or other falsy-but-present values correctly if fields are ever added.

### `get_started` full-config path intentionally omits the worksheet tip

The worksheet tip (`> **Tip:** Fill out setup-worksheet.md...`) appears in `noConfigText()` and `partialConfigText()` but not `fullConfigText()`. Professors who are already fully configured have no use for the worksheet — showing it to them would be noise.

There is a regression test: `it('full-config text does not mention get_setup_worksheet', ...)` in `tests/get-started.test.ts`.

### `setup_institution` description updated

During code review, it was noted that after the SP13 change the description no longer documented the no-worksheet (standalone interactive) path. The final description:

> "Re-run the setup wizard to update institution config (brand colors, Canvas URL, API token). Run this to change institutions or rotate credentials. Optionally pass worksheetContent from a filled setup-worksheet.md to pre-fill all answers."

### `readFileSync` at call time, not module load time

`getSetupWorksheet()` calls `readFileSync` inside the function body rather than at module initialization. `WORKSHEET_PATH` is computed once at module load (it's a static path), but the I/O is deferred to call time. For an MCP tool called infrequently (a professor fetches the worksheet once per setup session), synchronous read is fine.

## Reasoning for Next Sprint

v1.1.0 closes the worksheet loop. Natural next investments based on usage patterns:

1. **Professor feedback loop** — v1.1 ships to professors. The worksheet is new; real usage will reveal which fields they skip, which they struggle with, and whether the summary UX is clear.

2. **Brand URL fetching** — The wizard stores `brandUrl` in `institution.json` (added in v1.0). A `fetch_brand_colors` tool that fetches the URL and returns structured hex color candidates would let the AI host suggest colors rather than requiring the professor to look them up manually.

3. **Worksheet validation** — `parseWorksheet` currently accepts any string and returns whatever it can extract. A `validateWorksheet()` that returns specific error messages ("Primary color looks like a color name, not a hex value") would help professors catch mistakes before the wizard runs.

## SP14 — Post-v1.1.0 Work (2026-05-16/17)

No version bump yet. These sprints extend v1.1.0 on the existing `master` branch.

### SP14a — `fetch_brand_colors` (shipped 2026-05-16)

**Commits:** `c84cb00` → `d409d19` (5 commits). 378 tests passing.

**What it does:** New MCP tool that takes a brand standards URL, fetches the HTML and up to 5 linked stylesheets, extracts hex colors, and returns a suggested primary/secondary pair plus a full ranked list. No Canvas API calls. No wizard changes.

**New files:**
- `src/utils/color-extraction.ts` — `ColorEntry`, `ColorSuggestion` types; `extractColors()`, `suggestColors()` (pure, no I/O)
- `src/tools/fetch-brand-colors.ts` — `fetchBrandColors(url)` (HTTP + formatting)
- `tests/color-extraction.test.ts` — 16 tests
- `tests/fetch-brand-colors.test.ts` — 6 tests

**Design decisions:**

**D1: URL as parameter, not read from `institution.json`**
The tool takes `url` directly from the professor (or AI host) rather than reading `brandUrl` from the saved config. Why: the tool is most useful *before* setup is complete, when no config exists yet. Reading from config would also require the wizard to have run first, creating a chicken-and-egg problem (you need colors to run setup, but setup stores the URL).

**D2: CSS variable names first, frequency fallback**
`suggestColors()` uses CSS variable names (`--color-primary`, `--brand-blue`, `--main-color`) as the primary signal for which color is "primary" — they're an explicit declaration of intent by the institution's design team. Raw frequency is the fallback when no variables are present. Why: a structural color like `#000000` or `#ffffff` often appears more frequently than the branded blue, so pure frequency ranking produces wrong suggestions. CSS variable names are a reliable authority signal.

**D3: HSL lightness for structural color detection, not WCAG relative luminance**
`isStructural()` uses HSL lightness (`hsl.l < 12` for near-black, `hsl.l > 88` for near-white) rather than WCAG relative luminance. Why: WCAG luminance for `#0033A0` (University brand blue) is ≈5% — below the 12% threshold — which would incorrectly flag it as "near-black" and filter it from suggestions. HSL lightness for `#0033A0` is ≈31%, correctly classified as a branded color. The test `'does not mark branded blue (#0033A0) as structural'` was added specifically to catch this regression.

**D4: Tool + utility split**
Pure extraction logic (`extractColors`, `suggestColors`) lives in `src/utils/color-extraction.ts` with no I/O. HTTP and formatting live in `src/tools/fetch-brand-colors.ts`. Why: the pure functions are testable without mocking HTTP. The 16 unit tests run against raw CSS strings — fast, reliable, no network.

**D5: No new dependencies**
Uses the existing `color` package (already in `dependencies` for `contrast.ts`) for HSL conversion. Uses Node.js 18+ built-in `fetch` with `AbortController` for timeout. Why: adding a new HTTP library or color parser would increase install size for a tool that's already solved by what's already there.

**D6: Failed stylesheet fetches silently skipped**
If a linked stylesheet 404s or times out, the error is caught and `''` is returned for that stylesheet. Why: brand standards pages often reference CDN-hosted CSS that requires cookies or referrer headers. One broken stylesheet should not abort color extraction from the stylesheets that did load.

**D7: 10-second timeout, max 5 stylesheets**
These are practical limits based on what a brand standards page actually contains. Real brand pages rarely link more than 3 stylesheets. 10 seconds is long enough for slow institutional servers. Both constants are named (`FETCH_TIMEOUT_MS`, `MAX_STYLESHEETS`) so they're easy to adjust.

### SP14b — Worksheet Validation (designed 2026-05-17, not yet implemented)

**Spec:** `docs/superpowers/specs/2026-05-17-sp14b-worksheet-validation-design.md`

**What it does:** Adds `validateWorksheet(defaults: WizardDefaults): string[]` to `src/utils/worksheet.ts`. Checks only three fields that would cause wizard crashes or Canvas API failures if malformed. Exposed as a guard inside `setup_institution` (blocks before the wizard starts) and as a new `validate_worksheet` MCP tool professors can call explicitly.

**Design decisions:**

**D1: Validate `WizardDefaults` (parsed object), not raw markdown**
`validateWorksheet` takes the output of `parseWorksheet()` — a structured object — rather than the raw worksheet string. Why: parsing and validation are separate concerns. `parseWorksheet` already handles the markdown format; `validateWorksheet` only needs to reason about field values. This makes both functions independently testable.

**D2: Format-only validation — no required-field checks**
If a field is absent (`undefined`), it passes silently. Why: the wizard prompts interactively for anything missing. Flagging absent optional fields as errors would produce false alarms for professors who prefer to answer some fields interactively. The worksheet is designed to pre-fill what you have, not force you to fill everything.

**D3: Only three wizard-critical fields**
`primaryColor`, `secondaryColor`, and `canvasUrl` are the only fields checked. Why: these are the only values that cause crashes or immediate failures — `Color()` throws on a malformed hex, and Canvas API calls fail instantly on a non-`https://` URL. Other fields (`professorEmail`, `favoriteCourses`, `panoptoDomain`) may cause problems later but don't block the wizard from running.

**D4: Error messages include the bad value and an example**
Each error string quotes the offending value and shows an example of what it should look like: `Secondary color "D64309" is not a valid 6-digit hex. Example: #D64309`. Why: professors should be able to fix the issue without re-reading the worksheet documentation. Quoting the bad value confirms which field has the problem; the example removes ambiguity about the expected format.

**D5: `formatWorksheetErrors` exported from `validate-worksheet.ts`, imported into `index.ts`**
Both `setup_institution` and the `validate_worksheet` tool produce identical error output. The formatting function is exported from `src/tools/validate-worksheet.ts` and imported into `src/index.ts`. Why: DRY — if the error format changes, it changes in one place. The alternative (duplicating the format in the handler) would silently diverge.

**D6: Block in `setup_institution`, don't warn-and-proceed**
When validation errors are found, `setup_institution` returns immediately with `isError: true` and the error list. Why: running the wizard with a known-bad hex would either crash `Color()` or silently store a malformed color in `institution.json`. Either outcome is worse than stopping and asking the professor to fix the worksheet. The wizard is not a repair mechanism for malformed input.
