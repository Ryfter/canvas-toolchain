# Canvas Design Studio v1.0.0 — Agent Handoff

**Date:** 2026-05-15  
**Version shipped:** 1.0.0 (npm: `canvas-design-mcp@1.0.0`)  
**Audience:** Any agent or developer picking this up cold — Codex, Gemini, Claude, or human

This document explains what changed in v1.0.0, why the decisions were made, and what comes next. It is the orientation document for any agent resuming work on this project.

> **Superseded:** v1.1.0 has shipped. For the current handoff, see [`docs/v1.1-handoff.md`](v1.1-handoff.md).

## What v1.0.0 Is

v1.0.0 is a **first-professor experience** release. Feature development is complete as of v0.9.8. Every change in v1.0.0 is polish: better onboarding, richer errors, and self-service orientation.

**It adds:**
- Three orientation docs in `docs/`
- A new `get_started` MCP tool
- A brand standards URL field in the setup wizard
- Rich structured error messages with ChatGPT help links across all high-impact tools
- A post-setup summary replacing the previous "setup complete" console output

**It does not add any new Canvas functionality.** No new tools except `get_started`, no new Canvas API integration, no schema changes beyond `brandUrl?: string` in `InstitutionConfig`.

## What Changed and Why

### `docs/start_here.md` (new)

**Why it exists:** The MCP tool list in Claude doesn't explain which tools work without setup, what the three entry points are, or how to start. New professors would open Claude, see 23 tools, and not know where to begin. `start_here.md` is designed to be read by the AI host at session start — it orients both the AI and the professor before any tools are called.

**Key design decision:** The AI host note is at the very top in a blockquote, before the professor-facing content. This is intentional — AI hosts read linearly, professors skim and jump to sections.

**Where it lives:** `docs/start_here.md`

### `docs/troubleshooting.md` (new)

**Why it exists:** Error messages from Canvas tools were plain strings. When something broke, a professor had no path forward except asking for help. This doc provides a complete error reference with Symptom / Cause / Fix for every known error category.

**Key design decision:** Every entry in the doc matches the structure of the rich error format in the code. The `▶ Get help: https://chatgpt.com/?q=...` link pattern is documented in the introduction so professors know what it is before they see it.

**Where it lives:** `docs/troubleshooting.md`

### `docs/setup-worksheet.md` (new)

**Why it exists:** The setup wizard asks for values that professors need to look up (hex colors, Canvas URL, API token location). Without preparation, professors stop mid-wizard to hunt for these. The worksheet lets them gather everything at their own pace before running the wizard. It also serves as a reference during the wizard for first-timers who get confused by the prompts.

**Key design decision:** The brand standards URL section is first — it's the one field that can save all the other color lookups. The doc explains *why* each field matters, not just what value to enter.

**Where it lives:** `docs/setup-worksheet.md`

### `src/utils/errors.ts` (new)

**Why it exists:** Before v1.0.0, each tool returned ad-hoc error strings. The `publish.ts` 401 error said something different from the `list-courses.ts` 401 error. There was no ChatGPT help link, no cause explanation, no fix steps.

**The pattern:**
```typescript
formatError({
  title: 'Canvas API — 401 Unauthorized',
  message: 'Your API token was rejected by Canvas.',
  cause: 'The token in your institution config is invalid, expired, or was revoked.',
  fix: ['Step 1', 'Step 2', ...],
  context: 'context string that gets URL-encoded into the ChatGPT help link',
})
```

**Key design decision:** `makeHelpUrl` encodes `Canvas Design Studio error: [context]` as a ChatGPT query. When a professor clicks the link, ChatGPT is pre-filled with enough context to give useful help. If they use a different LLM, they can copy the decoded text from the URL.

**Where it lives:** `src/utils/errors.ts`

### `src/tools/get-started.ts` (new)

**Why it exists:** AI hosts have no way to know what state a professor's installation is in without calling tools. `get_started` reads `institution.json` and returns a tailored orientation — what's active, what setup would unlock, quick-start prompts, and a Context7 hint.

**Three states:**
1. **No config** — lists the 15 tools that work without any setup, prompts `setup_institution`
2. **Config present but no API token** — shows active tools, lists what an API token enables (`list_canvas_courses`, `publish_to_canvas`)
3. **Fully configured** — lists all active capabilities

**Key design decision:** The tool never throws. If `institution.json` is missing, it returns the "no config" orientation rather than erroring. This makes it safe to call as the first tool in any session.

**Where it lives:** `src/tools/get-started.ts`

### `src/wizard.ts` changes

**What changed:**
- Every prompt now has a plain-English explanation and an example inline in the message string
- A new `brandUrl` field is added after institution name — professors paste their brand standards URL and the AI host can fetch it to suggest colors
- Canvas URL validation now also catches trailing slashes
- API token validation threshold raised from 10 to 20 characters
- Professor email now validates format
- The end-of-wizard `console.log` block (which printed raw values) is replaced with `formatSetupSummary(config)` — a formatted markdown summary table

**Why:** The old wizard was functional but gave professors no guidance on what each field meant. The inline explanations are in the `message:` parameter of each `@inquirer/prompts` call so they appear directly in the wizard flow.

**Key design decision:** The brand URL field does NOT fetch the URL itself — the MCP server is stateless and has no LLM. The URL is stored in `institution.json` as `brandUrl`. When the AI host runs the wizard, it can be asked to fetch the URL and extract colors. The tool returns the URL in the setup summary so the AI host can act on it.

### Error enrichment across tools

**Files changed:** `src/tools/publish.ts`, `src/tools/list-courses.ts`, `src/tools/panopto.ts`, `src/index.ts`

**What changed:** Every `missingTokenError`, `apiError`, empty-results response, and not-configured response now calls `formatError()`. The output is consistently structured with title, message, cause, numbered fix steps, and a ChatGPT help URL.

**`src/index.ts` also adds:** `configExists()` guards before `loadConfig()` in the `generate_canvas_page` and `ingest_assignment_folder` handlers. Previously these would throw a raw error if no config existed; now they return a structured "Setup Required" error with fix steps.

## How to Publish

The publish mechanism is unchanged from previous versions:

```bash
git tag v1.0.0
git push origin master
git push origin v1.0.0
git push backup master
```

Pushing the `v1.0.0` tag triggers GitHub Actions which publishes `canvas-design-mcp@1.0.0` to npm and the Docker image to `ghcr.io/ryfter/canvas-design-studio:1.0.0` (also tagged `latest`).

## Reasoning for Next Sprint

Feature work is complete. The most valuable next investments based on v1.0 polish work:

1. **Professor feedback loop** — v1.0 ships to professors. Gather what they actually get confused by. The troubleshooting doc lists the errors that exist; real usage will reveal which ones happen most.

2. **Brand URL parsing** — the wizard stores `brandUrl` but the AI host does the color extraction. A `fetch_brand_colors` tool that fetches the URL and returns structured color candidates would close this loop cleanly.

3. **`setup_institution` worksheet integration** — the spec designed a worksheet-reader flow where the wizard reads a completed `setup-worksheet.md` and pre-fills answers. This was deferred. Low implementation cost, high first-run experience value.
